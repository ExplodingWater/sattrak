# macOS and Debian installers

The native installer targets build desktop installers with all offline assets,
the sattrak icon, and launchers that prepare the user's writable installation.
The source checkout is not needed after installation. Installers never run the
simulation as root or write to user home directories from privileged scripts.

## Build

Use a native compiler for the architecture you are shipping. The packager checks
the actual Mach-O/ELF headers rather than guessing from CMake or Python's host
architecture, which can be misleading under Rosetta.

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release \
  -DSATTRAK_RELEASE_VERSION=1.0.0-preview.20261109
cmake --build build --parallel 4
ctest --test-dir build --output-on-failure
```

On macOS:

```sh
cmake --build build --target macos_installer
```

`build/installers/` contains `sattrak.app`, a drag-install `.dmg`, a native
Installer.app `.pkg`, and SHA-256 files. Both installer formats install the same
app; choose one. The PKG installs to `/Applications/sattrak.app`. For the DMG,
open it and drag `sattrak.app` onto Applications, then launch from Finder.
The package's initial payload and desktop launcher must have the same CPU
architecture. Finder/Dock branding is preserved when the launcher hands off to
the managed game executable.

On Debian 12+ (amd64 or arm64):

```sh
sudo apt-get install build-essential cmake python3 dpkg-dev desktop-file-utils \
  libcurl4-openssl-dev libgl1-mesa-dev xorg-dev libasound2-dev
cmake --build build --target debian_installer
sudo apt install ./build/installers/sattrak-1.0.0-preview.20261109-debian-amd64.deb
```

Use the arm64 filename on an arm64 machine. The `.deb` includes `/usr/bin/sattrak`,
a read-only bootstrap payload at `/usr/lib/sattrak/payload`, a desktop-menu entry,
a 256px application icon, license notices and package documentation. Shared-library
dependencies are generated by `dpkg-shlibdeps` from the actual binaries. Python
3.9+ and CA certificates are declared dependencies. No post-install script copies
files into user homes. Removing/purging the package preserves user data.

The `.deb` must be built against Debian's libraries; packaging a Mac binary or an
arbitrary newer-Ubuntu binary as a Debian installer is rejected/unsupported. The
workflow uses Debian 12 containers to maintain the intended glibc baseline.

## User files and updates

On first launch, the native desktop launcher copies the supplied payload into a
complete per-user release and starts it. Later launches use that active release.
A newer desktop installer seeds its newer payload when no existing session holds
a lock. An older installer never downgrades an already newer per-user app.

Default roots:

- macOS: `~/Library/Application Support/sattrak/installation`
- Debian: `${XDG_DATA_HOME:-$HOME/.local/share}/sattrak/installation`

Within that root, `user-data/` holds preferences and recordings, `releases/` holds
complete payloads, and `current` identifies the active version. First launch needs
space for a per-user copy of the bundled assets (roughly another 300 MB), in
addition to the system app/package. Multiple users each have their own state and
active release. The developer override `SATTRAK_USER_INSTALL_ROOT` selects another
absolute, owned, managed folder for isolated testing; unmanaged folders are refused.

The existing automatic updater operates on this per-user installation after the
app closes. It never rewrites `/Applications/sattrak.app`, `/usr/bin/sattrak`, or
other dpkg-managed files. Python 3.9+ on PATH is needed for that helper; the native
Mac app itself launches without Python. Debian installs Python as a dependency.
Keep the matching `.tar.gz` update archives on each GitHub release as well as the
initial `.dmg`/`.pkg`/`.deb` installers. See [app updates](APP_UPDATES.md).

Preferences/recordings from an older source checkout stay in its existing launch
folder. To migrate them, close all sessions and copy the desired settings and
`local/recordings` into the new `user-data/` folder; the installer does not scan or
delete old source-build data.

## macOS signing and notarization

Default builds are for development/testing: code is signed ad hoc and the PKG is
unsigned. They are not notarized, so they are not yet a public Gatekeeper-ready
release. No quarantine attributes are removed or bypassed by the installer.
For public distribution, configure your own Developer ID identities:

```sh
cmake -S . -B build \
  -DSATTRAK_APP_SIGNING_IDENTITY="Developer ID Application: Your Name (TEAMID)" \
  -DSATTRAK_INSTALLER_SIGNING_IDENTITY="Developer ID Installer: Your Name (TEAMID)"
cmake --build build --target macos_installer
```

The builder signs the engine, launcher and app bundle, verifies the signature, and
signs the Installer product when an installer identity is supplied. Submit the
resulting containers with your configured notary keychain profile, then staple:

```sh
xcrun notarytool submit build/installers/sattrak-VERSION-macos-arm64.dmg \
  --keychain-profile sattrak-notary --wait
xcrun stapler staple build/installers/sattrak-VERSION-macos-arm64.dmg
xcrun notarytool submit build/installers/sattrak-VERSION-macos-arm64.pkg \
  --keychain-profile sattrak-notary --wait
xcrun stapler staple build/installers/sattrak-VERSION-macos-arm64.pkg
```

Replace VERSION and architecture with the actual artifact names. Credentials and
private keys are not embedded in the repository. Recompute the checksum sidecars
after stapling, since stapling changes container bytes.

## CI and validation

The **Native update packages** workflow builds/tests installers and update archives
for Apple Silicon, Intel Mac, Debian amd64 and Debian arm64. Debian jobs install
the resulting package in an isolated container, validate its desktop entry, and
launch its native diagnostic as a normal user. macOS jobs verify the app signature
and disk image. The workflow uploads artifacts without publishing a GitHub release.

CTest covers native launcher first launch, state preservation, update-helper lock
handoff, installer upgrades, refusing unmanaged folders and avoiding downgrades,
as well as platform-specific package layout and metadata. On a real desktop, also
verify Finder/application-menu launch, graphics/audio, updating, and uninstall.
